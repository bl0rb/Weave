# Vertragsindex

`contracts/` liegt zentral in der Wurzel dieses Monorepos, nicht mehr in einem einzelnen Dienst-Verzeichnis. Alle formalen Datenverträge zwischen den sechs Diensten (`services/ingest`, `services/knowledge`, `services/retrieval`, `services/runtime`, `services/api`, `services/tools`) sammeln sich hier, jeder unabhängig versioniert. Ein Verweis auf einen Vertrag ist deshalb immer relativ zur Repo-Wurzel, z.B. `contracts/chunk-store.md` — nie relativ zu einem einzelnen Dienst.

Sieben Verträge liegen aktuell hier:

### `frontmatter.schema.json`

Das YAML-Frontmatter, das jedes von `services/ingest` erzeugte Markdown-Dokument einleitet (`---\n{fields}\n---\n{body}`), als JSON Schema (Draft 2020-12). Erzeugt wird es von `services/ingest` (`_build_rag_frontmatter` in `app/services/paddle_service.py` sowie beim Confluence-Import); konsumiert wird es von `services/knowledge` beim Indizieren und von jedem weiteren RAG-System, das die erzeugten Markdown-Dateien liest. Additive Änderungen (neue optionale Felder) erhöhen nur die Minor-Version der im Schema referenzierten `$id`; eine Breaking Change (Pflichtfeld entfernt/umbenannt, Typ geändert, Enum-Wert gestrichen) erzwingt eine neue Datei mit neuer Major-Version (`frontmatter.v2.schema.json`), und `services/knowledge` muss beide Versionen parallel unterstützen, bis alle bereits verarbeiteten Dokumente auf die neue Version migriert sind.

### `openapi.json`

Der vollständige OpenAPI-3.x-Export der FastAPI-App von `services/ingest` — alle `/api/v1`-Routen inklusive Upload, Jobs, Mail-Ingest, Import, Webhooks, Collections-CRUD und -Registry (`GET /api/v1/collections/registry`), OpenWebUI-Push, sowie sämtliche Request-/Response-Schemas. Erzeugt wird er per `scripts/export_openapi.py` (nach jeder Routen- oder Schema-Änderung neu laufen lassen und den entstehenden Diff committen); konsumiert von `services/api` und `services/knowledge`, die beide gegen diesen eingefrorenen Vertrag programmieren (Client-Typen, Contract-Tests), statt gegen eine laufende Instanz zu raten oder Ingest-Code direkt zu importieren. Additive Änderungen (neue optionale Felder, neue Routen) sind unkritisch; Breaking Changes (Pflichtfeld entfernt/umbenannt, Response-Typ geändert, Route entfernt) müssen vor dem Mergen mit `services/api` und `services/knowledge` abgestimmt werden.

### `chunk-store.md`

Das Tabellenschema von `documents`/`chunks`/`collections` in der `weave_knowledge`-Datenbank — ein bewusst geteiltes Read-Model und die einzige Ausnahme von ADR-0004s Regel "ein Postgres-Cluster, aber eigene Datenbank pro Service" (siehe auch ADR-0005). Schreibender Owner ist `services/knowledge` (alle Alembic-Migrationen, jedes `INSERT`/`UPDATE`/`DELETE`); `services/retrieval` liest read-only direkt auf derselben Datenbank über eine eigene DB-Rolle mit reinen `SELECT`-Grants — kein eigenes Alembic, keine Schema-Änderung. Bei einer Abweichung zwischen diesem Dokument und dem tatsächlichen Code gewinnt `services/knowledge`s Definition in `app/models/models.py` und `alembic/versions/0001_init.py`. Additive Schema-Änderungen (neue nullable Spalte, neuer Index) sind ohne Koordination möglich; jede Breaking Change (Spalte umbenennen/entfernen, Typ ändern, `EMBEDDING_DIMENSION` ändern) erhöht die Vertrag-Version und erfordert ein koordiniertes Deployment-Fenster beider Dienste — ein bereits laufendes `services/retrieval` darf nie gegen ein Schema laufen, das eine ihm unbekannte Breaking Change bereits enthält.

### `internal-chat.md`

Der interne `POST /internal/chat`- (und `/internal/chat/stream`-) Vertrag zwischen Gateway und Chat-Pipeline. Anbieter ist `services/runtime`, das die Route und die dahinterliegende Pipeline implementiert (`app/api/internal.py`, `app/services/chat.py`) — jede Feldbedeutung ist 1:1 aus den echten Pydantic-Schemas (`app/schemas/chat.py`/`app/schemas/bot.py`) extrahiert, nicht aus README-Prosa. Konsument ist `services/api`, das ausschließlich über seinen `runtime_client.py` dagegen spricht, sowohl von `POST /v1/chat` als auch vom OpenAI-kompatiblen `POST /v1/chat/completions`. Additive Änderungen (ein neues optionales Response-Feld, ein neuer `intent`-Wert) sind unkritisch, da `services/api` unbekannte Felder ignoriert; eine Breaking Change (Pflichtfeld entfernt/umbenannt, ein bestehendes Fehlerbild geändert) erhöht die Vertrag-Version und muss in `services/runtime` UND in `services/api`s `runtime_client.py`/`openai_compat.py` im selben Koordinationsfenster geändert werden, bevor deployt wird.

### `n8n-flow.md`

Der Vertrag für n8n als optionalen Bot-Provider: Ein Chat-Turn wird per signiertem Webhook an einen externen n8n-Agentenflow delegiert, verpackt mit einem kurzlebigen, HMAC-signierten Delegations-Token, das dem Flow exakt den Lese-Umfang des anfragenden Menschen leiht. Anbieter/Aussteller ist `services/runtime` (`app/services/n8n_client.py`, `app/services/delegation.py`, `app/services/chat.py`s `_run_n8n_turn`); Konsumenten sind der jeweilige n8n-Flow (adressiert über `bot.n8n.webhook_url`) sowie, sobald dieser Flow das Token einlöst, `services/tools` selbst als Token-Verifizierer. Beide kryptographischen Prüfungen (Anfrage-Signatur, Delegations-Token) unterscheiden bei einer Abweichung nie den genauen Fehlergrund — falsche Signatur, abgelaufen, manipulierte Payload — und liefern immer denselben generischen Fehler; einzige Ausnahme ist ein leeres/fehlkonfiguriertes `WEAVE_DELEGATION_SECRET` selbst, das mit `503` beantwortet wird statt mit dem generischen Verifikationsfehler. Additive Änderungen brauchen keine Versionserhöhung; ein geändertes Token-Format oder eine geänderte Signaturberechnung ist breaking und erfordert ein koordiniertes Deployment-Fenster über `services/runtime`, jeden bestehenden n8n-Flow und `services/tools`' Verifizierer gleichzeitig.

### `events/document.processed.md`

Das Webhook-Event, mit dem `services/ingest` seine Konsumenten (primär `services/knowledge`) über ein erfolgreich verarbeitetes Dokument benachrichtigt (`job_id`, Frontmatter, Quality-Signale, `markdown_url`). Ausgelöst wird es aus dem Job-Abschluss-Hook in `app/workers/tasks.py`, nur für Jobs mit aktivierter, eingetragener Webhook-Verbindung; das zugehörige JSON-Schema liegt in `events/document.processed.schema.json` und referenziert `frontmatter.schema.json` per `$ref`, statt Felder ein zweites Mal zu duplizieren. Ein Konsument verifiziert die HMAC-SHA256-Signatur im `X-Weave-Ingest-Signature`-Header gegen den rohen Body, um Authentizität sicherzustellen. Bei einer inkompatiblen (Breaking-)Änderung erhält der Vertrag eine neue URL-Version (z.B. `/v2`); bestehende Konsumenten bleiben auf v1, bis sie aktiv upgraden — additive Felder in `signals` oder auf oberster Ebene brechen dagegen nichts, da unbekannte Felder ignoriert werden.

### `events/collection.updated.md`

Das Webhook-Event, mit dem `services/ingest` jede aktivierte Webhook-Verbindung benachrichtigt, sobald sich der Registry-Eintrag einer Collection ändert — insbesondere die Lese-ACL `read_teams`. Ausgelöst direkt aus `POST /api/v1/collections` bzw. `PATCH /api/v1/collections/{id}` (`app/api/routes.py`), unabhängig vom Owner der jeweiligen Verbindung, weil eine Collection eine globale Ressource ist. Primärer Konsument ist `services/knowledge`, das seine `collections`-Tabelle synchron hält; der Event selbst ist ausdrücklich nur ein Anstoß, keine Datenquelle — ein Konsument reagiert, indem er `GET /api/v1/collections/registry` erneut abruft, statt dem Payload-Inhalt zu vertrauen. Bleibt dieser Anstoß aus oder wird er verpasst, bemerkt ein Konsument die Änderung spätestens beim nächsten periodischen Sync-Poll gegen die Registry; bis dahin kann ein Team faktisch noch auf Dokumente zugreifen, die ihm gerade entzogen wurden — genau dieses Zeitfenster soll der Event schließen.
