PaddleDoc → Weave  ·  Transformationsplan

Weave Bauplan

PaddleDoc wird nicht ersetzt — es wird zum Dokumenten-Compiler eines modularen Bot-Systems. Sechs Services, zwei Pipelines, ein Prinzip: RAG ist ein Werkzeug des Bots, nicht der Bot selbst.

Stand: 06.09.2026 · v0.1.0 · Phasen 0–4.5 und 6 vollständig, Phase 5 (Aktions-Werkzeuge) offen · Testsuiten grün über neun Dienste Basis: PaddleDoc-Codeanalyse (Backend · Pipeline · Frontend · Infra) Quelle: new_apps.md
01

Leitideen

Drei Architektur-Entscheidungen aus dem Konzept, die alles Weitere bestimmen.

Nicht jede Anfrage braucht RAG

Ein Intent-Router steht vor dem Retrieval: conversational, knowledge, document, action, complex. Nur der knowledge-Pfad ruft die Suche auf — das spart massiv Retrieval-Aufrufe.

PaddleDoc bleibt

Es löst eine andere Aufgabe als der Bot: Dokumente → strukturiertes Markdown + Metadaten. Als Weave-Ingest wird es zum eigenständigen Ingestion-Service mit Event-Ausgang.

Bot = Konfiguration

Bots sind YAML-Definitionen (Modell, System-Prompt, Knowledge-Bases, Tools, Permissions) auf einer gemeinsamen Runtime — legal-support, hr-support, it-support ohne neuen Code.

03

Die sechs Services

Der Schnitt, wie er zu Beginn geplant wurde: sechs eigene Repositories, von denen nur Weave-Ingest mit Code startet — dem kompletten PaddleDoc. Seit Phase 6 liegen alle sechs als services/<dienst> in diesem Monorepo; die Ursprungs-Repos sind eingefroren.

Weave-Ingest

Dokumenten-Compiler

PDF, DOCX, PPTX, XLSX, Bilder, EML und Confluence → strukturiertes Markdown mit YAML-Frontmatter, Content-Hash-Versionierung, A/B/C-Quality-Gates, Webhooks. Behält Frontend, Mail-Ingestion, Benchmarks und Importe.

Basis: PaddleDoc (komplett)

Weave-Knowledge

Index-Pipeline

Konsumiert das document.processed-Event: strukturbewusstes Chunking (Headings, Seitenmarker, Breadcrumbs), Metadata-Enrichment, Embeddings, Schreiben in Postgres + pgvector. Ersetzt direkte Pushes an externe Wissenssysteme durch eine kontrollierte interne Veröffentlichung.

Basis: neu · Muster aus Ingest

Weave-Retrieval

Hybrid Search

Ein Endpoint: Query rein, Top-Chunks raus. Vector Search + BM25/Fulltext parallel, Rank-Fusion, Reranking (top_k 20 → final 5). Metadaten-Filter (Team, Department, Kunde, Sprache) sind first-class.

Basis: neu

Weave-Runtime

Bot-Orchestrator

Intent-Router entscheidet pro Anfrage: direkte Antwort, Retrieval, Dokument-Verarbeitung, Tool oder Workflow. Bots als YAML-Konfiguration, LLM-Provider-Abstraktion, Response Guard mit Quellenangaben.

Basis: neu · VL-Connections aus Ingest

Weave-Tools

Action-Layer

MCP-Dienst und REST-Spiegel mit rechte-gebundener Suche. Der Umfang kommt aus dem Token, nie aus den Werkzeug-Argumenten. Die zunächst hier entstandene Chat-Oberfläche ist mit dem Monorepo ein eigener Dienst geworden (services/chat). Offen bleiben die handelnden Werkzeuge: E-Mail, CRM, Web.

Teilweise umgesetzt · Phase 4.5c/d

Weave-API

Bot-Gateway

POST /v1/chat mit bot_id, conversation_id, message → answer, sources, trace. Auth (OIDC + API-Tokens), Rate-Limiting, Conversation State. Optional können OpenAI-kompatible Clients diese Gateway-Schnittstelle verwenden.

Basis: neu · Auth-Muster aus Ingest

05

Risiken & offene Entscheidungen

Aus der Codeanalyse — Kopplungspunkte in PaddleDoc, die der Service-Schnitt aktiv auflösen muss.

Eine Celery-Queue für allesAlle Tasks laufen heute über eine Default-Queue in Redis. Beim Split braucht jeder Service explizites Queue-Routing oder eigene Broker — sonst konsumieren sich die Worker gegenseitig die Tasks weg.
SECRET_KEY ist nicht rotierbarFernet-verschlüsselte Credentials (OIDC, Confluence, VL-Keys) hängen an einem Key, dessen Rotation alles invalidiert. Vor dem Split pro Service klären, sonst vererbt sich das Problem sechsfach.
Sichtbarkeits-Filter stecken in >10 Query-HelfernTeam-/Owner-Sichtbarkeit ist tief im Ingest-Backend verwoben. Entscheidung nötig: Zugriffskontrolle im Gateway (Weave-API) zentralisieren und Metadaten-Filter im Retrieval erzwingen — nicht in jedem Service neu implementieren.
Webhook-Delivery ist nicht idempotentJob-Verarbeitung dedupliziert per Content-Hash, die Auslieferung nicht. Weave-Knowledge muss doppelte Events verkraften — Idempotenz gehört in den Konsumenten (Phase 2).
Frontmatter-Konsistenz über fünf Enginespaddleocr, mail-eml, pypdf-fallback, spreadsheet-fallback und openai_vision müssen identische Frontmatter liefern; engine/used_fallback setzt heute der Aufrufer. Der Vertragstest aus Phase 1 ist die Absicherung.
Betriebslücken im BestandKein Session-Cleanup-Job, kein Orphaned-File-Audit, DB-Pooling auf Defaults, Worker-Logs auf 20.000 Zeilen gedeckelt. Vor dem Multiplizieren auf sechs Services in Ingest beheben.
GPU-Worker nicht überall portierbarDie GPU-Variante (paddlevl_1_6_0_9b) braucht NVIDIA-Runtime; das PaddleOCR-Modell-Volume ist groß. Bleibt ein Ingest-internes Deployment-Detail — darf nie zur Voraussetzung für andere Services werden.
