01

Die sechs Dienste

Zwei Pipelines: offline verwandelt Ingest Dokumente in durchsuchbare Chunks, online beantwortet die Runtime Anfragen. Jeder Dienst hat eine eigene Datenbank — mit einer dokumentierten Ausnahme.

DienstPortDatenbankAufgabe
Weave-Ingest8000weave_ingestOCR, Markdown + Frontmatter, Quality-Gate, besitzt die Collections
Weave-Knowledge8001weave_knowledgeChunking, Embeddings, schreibt den Chunk-Store, spiegelt die Collection-Registry
Weave-Retrieval8002liest weave_knowledgeHybride Suche; Lese-Autorität für Collections. Einziger Dienst ohne eigene DB — siehe ADR-0005
Weave-Runtime8003keineIntent-Router, Bots als YAML, LLM, n8n, stellt Delegations-Token aus
Weave-API8004weave_apiGateway und Identitäts-Autorität: Nutzer, Tokens, Sitzungen, Gespräche
Weave-Tools8005 · 3001keineMCP-Dienst mit rechte-gebundener Suche; Chat-Oberfläche
Warum Retrieval fremd mitliest

pgvector-Ähnlichkeit und tsvector-Ranking müssen als SQL in der Datenbank laufen. Ein API-Umweg würde Weave-Knowledge zwingen, die halbe Suche selbst zu bauen. Deshalb: Knowledge schreibt, Retrieval liest read-only über eine eigene Rolle mit ausschließlich SELECT. Das Schema ist dadurch ein Vertrag (contracts/chunk-store.md).

02

Lokal starten

Die Compose-Datei zeigt auf Registry-Images, die nie veröffentlicht wurden. Das Override baut alle sechs Dienste aus diesem Monorepo (services/<dienst>).

# Geheimnisse erzeugen (12 Pflichtwerte, siehe Abschnitt 04)
cd deploy
cp .env.example .env   # und die Werte füllen

# Bauen und starten — ohne OCR-Worker, der ist mehrere GB groß
docker compose -f docker-compose.weave.yml -f docker-compose.local.yml up -d --build

# OCR-Worker nachziehen, wenn du wirklich Dokumente verarbeiten willst
docker compose -f docker-compose.weave.yml -f docker-compose.local.yml \
  --profile ocr up -d weave-ingest-worker

Beenden mit down; die Daten bleiben in den Volumes. Erst down -v löscht auch die Datenbanken.

Port 3000

Das Ingest-Frontend will Port 3000. Ist der belegt, setze FRONTEND_PORT auf einen freien Port — sonst bricht der Start des ganzen Stacks mit address already in use ab.

03

Erstinbetriebnahme

Zwei Tokens entstehen erst, wenn der Stack schon läuft — das ist ein Henne-Ei-Problem, das sich nur in dieser Reihenfolge auflösen lässt.

  1. Ersten Administrator in Weave-Ingest anlegen

    Über die Setup-Seite des Ingest-Frontends. Der erste Nutzer wird automatisch Administrator.

  2. Dort einen persönlichen API-Token erzeugen

    In den Einstellungen. Dieser Token muss zu einem Administrator gehören: Weave-Knowledge holt die Collection-Registry über einen Admin-Endpunkt, weil sie die komplette Zugriffskarte des Systems ausgibt.

  3. Token eintragen und Knowledge neu starten

    Als WEAVE_KNOWLEDGE_INGEST_API_TOKEN in die .env, dann docker compose … restart weave-knowledge weave-knowledge-worker. Bis dahin läuft der Registry-Sync in ein 401 und die Collection-Rechte bleiben leer.

  4. Webhook-Verbindung in Ingest anlegen

    Damit verarbeitete Dokumente überhaupt bei Knowledge ankommen. Das Secret dieser Verbindung muss identisch zu WEAVE_KNOWLEDGE_WEBHOOK_SECRET sein, sonst weist Knowledge jedes Event mit 401 ab.

  5. Nutzer für die Chat-Oberfläche anlegen

    Rein tokenbasiert, kein Passwort nötig. Der Token wird genau einmal angezeigt.

    docker compose exec weave-api python -m app.cli \
  create-user --username matze --team legal

Diese sieben müssen in mehreren Diensten zeichengleich stehen. Sie sind die häufigste Fehlerquelle beim Aufsetzen — und die Symptome zeigen selten auf die Ursache.

06

Stille Fallen

Der wichtigste Abschnitt. Bei allen folgenden Fehlern stürzt nichts ab, es erscheint keine Fehlermeldung — es funktioniert einfach nicht, oder schlimmer: es funktioniert scheinbar.

EMBEDDING_MODELDie Suche findet nie etwas
Die Vektorsuche vergleicht ausschließlich Chunks, deren gespeicherter Modellname exakt dem konfigurierten entspricht. Weicht Retrieval von Knowledge ab, ist das Ergebnis eine leere Liste — nicht ein Fehler.
PrüfenBeide Werte vergleichen; der Volltextpfad funktioniert derweil weiter, was den Fehler verschleiert.
EMBEDDING_PROVIDERDer Index enthält Attrappen
Die Voreinstellung ist fake. Vergisst man sie produktiv, indiziert der Dienst klaglos weiter — aber mit deterministischen Pseudo-Vektoren, die keinerlei Bedeutung tragen. Die Suche „läuft", liefert nur Unsinn.
PrüfenGilt genauso für LLM_PROVIDER: bleibt er auf fake, antwortet jeder Bot mit Platzhaltertext, der bei flüchtigem Lesen wie eine Antwort aussieht.
DATABASE_URLDer Dienst schreibt in eine Datei im Container
Fehlt bei Ingest sowohl DATABASE_URL als auch die vollständige Kombination aus Host, Datenbank und Benutzer, fällt der Dienst still auf eine lokale SQLite-Datei zurück. Bei Retrieval ist der SQLite-Pfad sogar die Voreinstellung: bleibt sie stehen, wird eine leere lokale Datei durchsucht.
PrüfenNach dem Start einmal in den Containern printenv DATABASE_URL lesen — steht dort sqlite, ist etwas falsch.
RETRIEVAL_BASE_URLAntworten aus dem falschen Bestand
Zeigt der Wert bei Weave-Tools auf eine falsche, aber erreichbare Retrieval-Instanz, gibt es keinerlei Warnung — es kommen einfach Treffer aus einem anderen Korpus zurück.
PrüfenBesonders heikel, wenn Test- und Produktivumgebung nebeneinander laufen.
REDIS_URLAufträge verschwinden
Jeder Dienst hat laut ADR-0001 eine eigene logische Redis-Datenbank: Ingest 0, Knowledge 1. Kopiert man die URL eines Dienstes zum anderen, kollidieren Warteschlangen und Sperren — ohne Fehlermeldung. Bei Ingest kommt hinzu: fällt Redis aus, gibt das Rate-Limit still auf und lässt alles durch.
PrüfenDie Zahl am Ende der URL muss sich zwischen den Diensten unterscheiden.
CORS_ORIGINSAnmelden ist unmöglich
Der Wert steuert nicht nur CORS, sondern auch die Herkunftsprüfung gegen CSRF. Fehlt die echte Frontend-Adresse, werden alle schreibenden Anfragen mit 403 abgewiesen — auch der Login. Erwartet wird ein JSON-Array, nicht eine kommagetrennte Liste.
FormatCORS_ORIGINS='["https://app.example.com"]'
PUBLIC_API_URLDownloads zeigen ins Leere
Stimmt der Wert nicht mit der von außen erreichbaren Adresse überein, schlägt der OIDC-Login mit einem Redirect-Mismatch beim Provider fehl — und die Download-Links in Webhook-Payloads Richtung Knowledge zeigen auf eine falsche Adresse. Ingest selbst merkt davon nichts.
PrüfenMuss der Adresse entsprechen, unter der Browser und Nachbardienste den Dienst wirklich erreichen.
OIDC_ISSUERSSO ist unsichtbar statt kaputt
OIDC gilt genau dann als aktiviert, wenn Issuer und Client-ID gesetzt sind. Ist nur eines von beiden gefüllt, bleiben sämtliche Anmelderouten unregistriert und antworten mit 404 — kein Fehler, nur ein Feature, das scheinbar nicht existiert.
PrüfenEbenso: eine leere OIDC_POST_LOGIN_ALLOWED_URLS bedeutet, dass jedes return_to still ignoriert wird und der Nutzer nach dem Login auf dem Gateway landet statt in der Oberfläche.
PADDLE_DEFAULT_PROFILEEin Tippfehler fällt nie auf
Ein unbekannter Profilname wird kommentarlos auf die Voreinstellung zurückgesetzt — kein Log, kein Fehler. Die Verarbeitung läuft mit dem falschen Profil weiter.
PrüfenNach einer Profiländerung stichprobenweise die profile-Angabe im erzeugten Frontmatter kontrollieren.
UPLOADS_DIR RESULTS_DIRDer Worker findet die Datei nicht
API-Container und OCR-Worker müssen auf dasselbe Volume zeigen — einer schreibt, der andere liest. Unterschiedliche Pfade führen zu Datei-nicht-gefunden im Worker statt zu einem Konfigurationsfehler. Ohne persistentes Volume sind Uploads nach einem Neustart weg.
PrüfenBeide Container müssen dasselbe Volume an denselben Pfad mounten.
07

Echte Provider

Voreingestellt laufen Embeddings, LLM und Reranker als Attrappen: die Kette funktioniert vollständig, ohne Schlüssel und ohne Kosten. Für den echten Betrieb sind es drei Blöcke.

WofürVariablenWo
Embeddings EMBEDDING_PROVIDER=openai
EMBEDDING_BASE_URL · EMBEDDING_API_KEY
EMBEDDING_MODEL · EMBEDDING_DIMENSION		 Knowledge und Retrieval — zeichengleich
Sprachmodell LLM_PROVIDER=openai
LLM_BASE_URL · LLM_API_KEY · LLM_DEFAULT_MODEL		 nur Runtime
Reranker RERANK_PROVIDER=api
RERANK_BASE_URL · RERANK_API_KEY · RERANK_MODEL		 nur Retrieval
Reranker degradiert leise

Fällt der Reranker aus oder ist er falsch konfiguriert, scheitert die Suche nicht — sie liefert die unrerankte Reihenfolge zurück. Das ist gewollt (eine Suche darf nie am Reranker sterben), heißt aber: eine kaputte Reranker-Konfiguration merkst du nur an schlechteren Ergebnissen, nicht an einem Fehler. Im Trace steht rerank_error.

Modellwechsel bei Embeddings

Ein anderes Embedding-Modell macht den bestehenden Index unbrauchbar — die alten Vektoren liegen in einem anderen Raum. Nach dem Wechsel gehört ein vollständiger Reindex dazu: python -m app.cli reindex in Weave-Knowledge. Ändert sich zusätzlich die Dimension, braucht es vorher eine Migration.

08

SSO einrichten

Personal-Tokens bleiben für Maschinen der Weg; OIDC ist für Menschen. Beide führen zum selben Konto und demselben Limit.

VariableBedeutung
OIDC_ISSUERBasis-URL des Providers. Zusammen mit der Client-ID schaltet sie OIDC überhaupt erst frei
OIDC_CLIENT_ID
OIDC_CLIENT_SECRET		Zugangsdaten der registrierten Anwendung
OIDC_REDIRECT_URLMuss beim Provider zeichengleich hinterlegt sein
OIDC_TEAM_CLAIMAus welchem Claim das Team gelesen wird. Leer heißt: Nutzer ohne Team — und damit ohne lesbare Collections
OIDC_POST_LOGIN_ALLOWED_URLSErlaubte Rücksprungziele. Nur hier eintragen, was du wirklich kontrollierst
Warum die Rücksprung-Allowlist so eng sein muss

Nach erfolgreichem Login hängt das Gateway einen einmaligen Übergabe-Code an die Rücksprung-Adresse. Wer dort einen fremden Eintrag unterbringt, bekommt diesen Code — und damit eine gültige Sitzung. Die Prüfung vergleicht Schema, Host und Port exakt und lehnt Backslashes, Steuerzeichen und kodierte Pfadsprünge ab, weil Browser URLs anders lesen als Python.

Zuordnung über den Subject, nicht die E-Mail

Konten werden ausschließlich über den OIDC-Subject verknüpft. Das ist Absicht: Bei einer Zuordnung über die E-Mail-Adresse könnte sich jemand mit derselben Adresse bei einem anderen Provider auf ein bestehendes Konto aufschalten.

09

n8n und MCP

Beide bekommen exakt die Leserechte des Menschen, der gerade fragt — über ein kurzlebiges, signiertes Delegations-Token, in dem der erlaubte Collection-Umfang eingebettet ist.

VariableDienstBedeutung
WEAVE_DELEGATION_SECRETRuntime · ToolsSigniert und prüft das Token. Zeichengleich, sonst geht nichts
DELEGATION_TOKEN_TTL_SECONDSRuntimeGültigkeit, Vorgabe 300 Sekunden
TOOLS_BASE_URLRuntimeWird dem Flow mitgegeben, damit er zurückfindet
N8N_ALLOWED_BASE_URLSRuntimeErlaubte Webhook-Adressen. Leer heißt: n8n-Bots sind abgeschaltet
TOOLS_API_TOKENToolsMuss im Flow als eigene Zugangsdaten hinterlegt werden — ein Service-Geheimnis gehört nicht in einen Payload
Die Regel dahinter

Der erlaubte Umfang wird immer serverseitig aus der Identität abgeleitet. Ein Collection-Name aus einem Tool-Argument oder einer Modell-Ausgabe kann nur einschränken, nie erlauben. Und was ein Flow als Quelle zurückmeldet, ist eine Behauptung: Weave prüft jede gemeldete Quelle gegen den signierten Umfang und verwirft, was nicht passt — sichtbar im Trace als dropped_sources.

Die Webhook-Allowlist greift beim Laden

Eine Bot-Datei mit einer nicht erlaubten Adresse lässt sich gar nicht erst laden — der Fehler kommt beim Start, nicht beim ersten Aufruf. Das ist Absicht: Eine Konfigurationsdatei soll den Dienst nicht in beliebige Netze rufen lassen können.

10

Selbsttest

Läuft die Kette wirklich? Diese Reihenfolge prüft sie von außen nach innen — jeder Schritt setzt den vorherigen voraus.

# 1 — Alle Dienste erreichbar
for p in 8001 8002 8003 8004 8005; do curl -s localhost:$p/health; done
curl -s localhost:8000/api/v1/health   # Ingest hat einen eigenen Pfad

# 2 — Gateway erreicht die Runtime (leere Liste = Bots werden nicht geladen)
curl -s -H "Authorization: Bearer $TOKEN" localhost:8004/v1/bots

# 3 — Was darf dieser Nutzer lesen?
curl -s -H "Authorization: Bearer $TOKEN" localhost:8004/v1/collections

# 4 — Eine echte Antwort samt Trace
curl -s -X POST localhost:8004/v1/chat \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"bot_id":"general-assistant","message":"Hallo"}'
Wie man die Antwort liest

Der trace sagt, wo es klemmt. intent: conversational bei einer Wissensfrage heißt: Der Router hat sie nicht als solche erkannt. guard.reason: no_collections heißt: Der Nutzer hat kein Team oder keine freigegebene Collection. retrieval.candidates: 0 bei vorhandenen Dokumenten heißt fast immer: Die Embedding-Einstellungen von Knowledge und Retrieval passen nicht zusammen.

SymptomWahrscheinliche Ursache

Bot findet nie etwasEmbedding-Modell oder -Provider unterscheiden sich zwischen Knowledge und Retrieval
Antworten beginnen mit [fake-llm]LLM_PROVIDER steht noch auf fake
